# 衣影工坊内部 MVP 交付策略

日期：2026-10-11
适用范围：公司内部局域网，约 5–10 名使用者。

## 决策

项目继续按照 `CREATIVE_WORKFLOW_IMPLEMENTATION_20261010.md` 完成功能范围。内部 MVP 只简化工程证明和发布门槛，不删减产品能力：

- 保留 Product / Character / Scene 输入和商品事实锁；
- 保留 A/B/C 方向、Reality 六维、Prompt Preservation 和生产包版本；
- 保留人工选择、图片审核、分镜审核和视频最终审核；
- 保留现有图片生成、视频生成、任务中心、内容库和恢复语义；
- 保留有界自主真实性循环，默认关闭，启用时受授权、预算、次数和停止条件约束；
- 保留 Fake / Replay 作为开发验证手段，但不得把它们显示为正式合格或可交付结果。

## 适合当前规模的实现方式

首个可用版本采用单机局域网部署和单 worker 运行。数据库、对象存储、Provider 和任务执行沿用仓库现有配置，不新增微服务、消息队列、独立评分平台或复杂 Agent 集群。

实现顺序固定为：

```text
商品正面输入
→ 方向候选与人工选择
→ Reality / Prompt / Production Package
→ 用户授权
→ 图片生成
→ 人工审核与选择
→ 分镜/视频生成
→ 视频最终审核与下载
```

第一阶段先让这条主链在局域网可操作；多镜头扩展、真实自动 Critic、服务端自主循环接线和更复杂的生产包能力继续按任务书补齐，但不阻塞基础图片和视频生产使用。

## 轻量验收门槛

每个交付包只需要证明与本包直接相关的行为：

1. 构建、静态检查和相关单元测试通过；
2. 一条真实或隔离的主流程可完成；
3. 重复提交、权限越界、失败/未知状态和人工审核边界不回归；
4. 页面交互变更完成一次桌面和一次移动视口检查；
5. 报告明确写出未覆盖项。

本阶段暂不把以下内容作为内部 MVP 的阻塞项：

- PostgreSQL 多 worker 并发压测；
- 跨进程崩溃窗口的穷举证明；
- 全量迁移回滚演练；
- 多浏览器、多操作系统矩阵；
- 真实像素质量的统计显著性结论；
- 完整灾备、审计平台和高并发容量证明。

这些内容仍保留在任务书的后续增强清单中，不能被误写成已经完成。

## 使用边界

- 只允许公司内网和已配置账户访问；
- 真实 Provider 与付费能力由管理员配置开关控制；
- 自动真实性修订首版默认关闭；
- 任何 AI 评审结果都不能直接写入人工 `QUALIFIED`；
- 生产、正式部署、迁移和真实付费调用仍需要单独的人为批准。

## 近期开发优先级

1. 修复当前已知的 stop 审计记录缺口；
2. 建立一键内部 MVP 就绪检查，减少人工启动和排障成本；
3. 将导演规划结果逐步接入现有图片生产入口；
4. 再接视频固定执行和有界自主循环；
5. 最后补 PostgreSQL、多 worker 和真实质量收益验证。

这个顺序降低研发等待时间，同时保留任务书要求的最终能力路线。
